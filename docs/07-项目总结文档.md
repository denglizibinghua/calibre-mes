## 1. 项目概述

**自行车组装 MES（Manufacturing Execution System）** 是一套面向自行车组装车间的全流程生产管理平台。系统覆盖从工单下达到工序报工、质量检验、设备维修、安灯告警、库存管理和安全培训的完整制造执行过程。

### 1.1 项目定位

- **管理端（Web SPA）**：供计划员、管理员、质检主管使用，提供完整的 CRUD 管理、工作流操作、报表导出功能
- **移动端（微信小程序）**：供车间一线工人和质检员在现场使用，提供工单查看、工序报工、质检录入、扫码等便捷操作

### 1.2 项目结构

```
bike-assembly-mes/
├── bike-assembly-common/       # 公共模块：注解、常量、工具类、异常、统一响应
├── bike-assembly-pojo/         # 数据对象：Entity、DTO、VO、枚举（状态机）
├── bike-assembly-server/       # 核心服务：Controller、Service、Mapper、Config、AOP
├── bike-assembly-mes-web/      # Web 管理端：Vue 3 + Element Plus + TypeScript
├── bike-assembly-mes-miniapp/  # 微信小程序：uni-app + Vue 3 + TypeScript
├── sql/                        # 数据库脚本（初始化、迁移、种子数据）
└── docs/                       # 项目文档
```

## 2. 解决了什么问题

### 2.1 生产管理问题

| 业务痛点 | 解决方案 |
|---------|---------|
| 📋 **工单进度不透明**：工单状态靠口头传递或纸质单据，管理者无法实时掌握生产进度 | 工单→工序多级状态机，每个工序的每次状态变更都被记录在 `pro_status_transition_log` 表中，管理者通过 Web 端可实时查看每个工单的工序级进度 |
| 🔧 **工序操作混乱**：工人不知道哪些工序可以开始、哪些需要等待前序完成，容易造成生产顺序错误 | 前序工序完工后自动将后续工序设为"可开工"状态（READY），工人只能看到并操作自己可以进行的工序，防止越序生产 |
| 🔄 **返工流程不规范**：返工后可能跳过质检直接完工，导致质量问题流入下道工序 | 状态机强制约束：`REWORK → WAIT_INSPECTION`，返工完成后必须重新经过质检合格才能完工，形成闭环 |
| 🔁 **重复提交**：网络抖动或多次点击导致同一个操作被执行多次 | 客户端生成幂等键（UUID + 10min TTL）+ 服务端数据库唯一索引实现原子性幂等，保证同一操作只执行一次 |

### 2.2 质量管理问题

| 业务痛点 | 解决方案 |
|---------|---------|
| 🔍 **质检流程不标准**：检验结果口头传达，无结构化记录，无法追溯 | 每个需要质检的工序自动创建检验单（`qms_inspection`），包含结构化的检验项目（`qms_inspection_item`），逐项录入结果 |
| 📊 **质检结果难统计**：合格率、缺陷分布等数据无法自动汇总 | 报表模块提供质检报表（`QualityReportVO`），支持按时间/工单/工序维度统计合格率和缺陷分布，支持 Excel 导出 |
| 🔗 **质检与工序脱节**：检验结果不能自动触发下一步动作，工序状态需要手动更新 | 检验确认（`confirmInspection()`）在同一事务内自动联动工序状态：合格→完工+触发下道工序，不合格→待返工 |

### 2.3 系统安全与权限问题

| 业务痛点 | 解决方案 |
|---------|---------|
| 🔐 **多端接入安全**：Web 管理端和微信小程序共享同一后端，需要安全隔离 | 双通道 JWT：管理端和移动端使用独立的签名密钥（admin-secret-key / app-secret-key），密码学隔离 |
| 👥 **细粒度权限**：不同角色（计划员、操作员、质检员、管理员）应有不同的操作权限 | RBAC 三层权限：路由层（动态菜单加载）+ 组件层（v-permission 指令）+ API层（@RequirePermission AOP），后端为最终安全边界 |
| 🔑 **密码安全弱**：简单密码、密码永不过期、历史密码可重用 | BCrypt 加密 + 复杂度校验（大小写字母+数字+特殊字符）+ 最近5次密码防重用 + 密码过期 + 首次登录强制改密 + 5次失败锁定15分钟 |

### 2.4 数据一致性问题

| 业务痛点 | 解决方案 |
|---------|---------|
| ⚡ **并发冲突**：多人同时操作同一工单/工序时可能产生数据不一致 | MyBatis-Plus `@Version` 乐观锁（通用）+ 关键路径 CAS SQL（`WHERE status=? AND version=?`）消除 TOCTOU 竞态 |
| 📝 **操作无追溯**：不知道谁在什么时候做了什么操作 | `@OperLog` AOP 自动记录操作类型/操作人/IP/时间到 `sys_oper_log`，状态机每次转换记录到 `pro_status_transition_log` |

### 2.5 消息通知问题

| 业务痛点 | 解决方案 |
|---------|---------|
| 📡 **实时性差**：依赖轮询查询状态变更，延迟高、资源浪费 | RabbitMQ 事件驱动：5个独立队列（工单/库存/质量/设备/安灯），状态变更后异步推送事件消息 |
| 🛡️ **MQ故障影响业务**：消息中间件不可用时不应阻塞核心业务 | 安全降级设计：`@ConditionalOnProperty` 条件化装配 + `ObjectProvider` 延迟获取 + `try-catch` 包裹 MQ 发送，失败仅记录日志 |

```
1. HTTP Request

3. JwtTokenInterceptor → JWT校验 + 用户状态 + 权限加载 → BaseContext
4. PermissionAspect → @RequirePermission 校验
5. Controller → 参数校验 (@Validated)
6. Service → 状态机校验 + 幂等处理 + 业务逻辑 + CAS更新
```

## 6. 关键技术决策

### 6.1 为什么选择 MyBatis-Plus 而非 JPA？

- MyBatis-Plus 提供更灵活的 SQL 控制能力（CAS 原子更新、复杂 JOIN 查询）
- 内置分页插件、乐观锁插件，开箱即用
- 与 Spring Boot 3.x 深度集成，配置简单
- 团队更熟悉 MyBatis 生态

### 6.2 为什么用数据库幂等而非 Redis？

- 减少基础设施依赖（不需要额外部署 Redis）
- 数据库唯一索引天然支持 ACID 事务，与业务数据在同一事务中
- 通过 24 小时 TTL 的 `expire_time` 字段控制数据增长
- 幂等记录量不大（仅状态变更操作需要）

### 6.3 为什么用双通道 JWT 而非统一密钥？

- 管理端（Web）和移动端（小程序）面向不同用户群体，安全级别不同
- 一方密钥泄露不会影响另一方，实现密码学隔离
- 支持独立配置 Token 有效期（管理端可以更短）
- 支持独立撤销（可以单独撤销所有移动端 Token）

### 6.4 为什么用集中式状态机而非状态模式？

- 自行车组装工序固定，状态转换规则集中管理更清晰
- `EnumMap` + 静态初始化块的方式声明式定义，一目了然
- 不需要为每个状态创建类（避免类爆炸）
- 转换规则在 `StatusTransitionValidator` 一个地方维护，不会散落在 ServiceImpl 各处

### 6.5 为什么用 Caffeine 本地缓存而非 Redis？

- 权限信息变更不频繁（角色变更才需要刷新），本地缓存足够
- 30 分钟 TTL + Spring Event 主动驱逐，确保一致性
- 减少网络延迟（本地内存 vs 网络调用）
- 减少基础设施依赖

### 6.6 为什么 RabbitMQ 做安全降级？

- MES 系统核心是生产执行，消息通知是增强功能，不应阻塞主流程
- 开发环境可能没有 RabbitMQ，通过 `@ConditionalOnProperty` 条件化装配
- `ObjectProvider` + `try-catch` 确保即使 MQ 挂了，工单照样能下达、工序照样能报工

## 8. 开发规范

### 8.1 后端规范（苍穹外卖风格）

1. **分层架构**：Controller → Service(接口) → ServiceImpl → Mapper → MySQL
2. **Spring IoC**：所有组件由 Spring 容器管理，禁止手动 new
3. **构造器注入**：优先使用构造器注入（或按现有风格使用 `@Autowired`）
4. **Controller 职责**：仅做参数接收、参数校验、调用 Service、返回结果
5. **Service 职责**：业务逻辑、事务管理（`@Transactional`）、状态机校验
6. **Mapper 职责**：数据库操作（MyBatis-Plus BaseMapper + 自定义 SQL）
7. **DTO/VO/Entity 分离**：入参用 DTO，出参用 VO，持久化用 Entity
8. **禁止 TODO/伪代码/空方法**：所有代码必须真实可执行

### 8.2 安全规范（Spring Security 风格）

1. **密码**：BCrypt 加密，不存储明文，不打印日志
2. **Token**：不打印、不存储明文 Refresh Token，数据库仅存 SHA-256 哈希
3. **JWT**：校验签名、校验过期时间、校验 tokenType、校验 clientType
4. **权限**：后端 `@RequirePermission` 为安全边界，前端 `v-permission` 为 UI 辅助
5. **异常**：不向前端暴露堆栈、SQL、服务器路径，只返回友好消息

### 8.3 Git 规范

- **主分支**：`master`（生产就绪代码）
- **开发分支**：`dev-lzy`（当前活跃开发分支）
- **提交信息**：描述性提交信息，末尾添加 `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`
