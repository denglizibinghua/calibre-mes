## 1. 执行摘要

本项目（自行车组装 MES）后端代码质量整体较高：Spring Boot 分层、状态机、乐观锁、幂等、双通道 JWT、Token Rotation、全局异常分类等基础设施均已真实落地，工单/工序/质检/维修的后端主链在静态代码层面是完整且自洽的。但存在 3 个 P0、7 个 P1 级问题，其中最关键的是：

1. **全新环境初始化 SQL（init_database.sql）与质检实体/Service 严重漂移**：`qms_inspection` 表缺少 `inspection_round`、`parent_inspection_id`、`confirmed_by`、`confirmed_user_id`、`confirm_time`、`create_time` 6 个字段，而代码在创建/确认检验单时必然写入这些字段，导致新环境质检链路直接报 `Unknown column`。
2. **Web 端构建失败**：`quality/inspection.vue` 导入 3 个不存在的 API 导出；Web 工程内混入 8 个小程序版 API 模块和 uni-app 版 `utils/request.ts`。
3. **小程序质检录入弹窗提交按钮不可用**：质检弹窗“确认录入”在“该工序无质检项”时被 `canSubmitResult` 永久禁用，且模板直接改写 ref 数组下标在 uni-app 编译环境不可靠；2026-08-04 已修复（无质检项时可手动综合判定 + 显式更新方法）。原 AUD-101“小程序不发幂等键”经复核为误报，见第 8 节勘误。
4. **库存模块只有单据 CRUD**：没有"单据执行→库存增减→库存流水"，数据库也没有库存流水表，负库存与并发扣减完全未防护。
5. **安灯/维修在 Web 和小程序均为占位页**，与 README"已完成"声明冲突；JMReport（积木报表）是假集成（无依赖、Token 校验恒为 true、菜单指向不存在的组件）。

其余问题包括：管理端大量 CRUD 与全部报表接口无权限注解、RBAC 权限码前后端/数据库三处不一致、DEPT 数据权限有名无实、MQ 消费者只打日志、报表无分页无数据权限过滤、生产配置硬编码 DeepSeek Key 与微信 AppSecret 等。

## 7. 核心业务全链路审计

### 7.1 登录与认证 —— 结论：CODE_VERIFIED

- admin/app 使用不同签名密钥，拦截器按 `/admin/**`、`/app/**` 分别解析，Web Token 无法访问 App 接口、App Token 无法访问 Admin 接口（签名即隔离）。
- Access(30min)+Refresh(7d) 双 Token，Refresh 存 `user_refresh_token`（仅 SHA-256 哈希）；轮换时条件更新 `revoked=0`，重放检测会**全量吊销该用户所有会话**。
- 禁用（status=1）、锁定（5 次失败锁 15 分钟）、密码过期/强制改密均有登录态 + 拦截器双重校验。
- `BaseContext` 在拦截器 `afterCompletion` 清理，无泄漏。
- 风险：拦截器对缺失 `clientType`/`tokenType` 声明的旧 Token 放行（兼容性妥协），`TOKEN_TYPE_FULL` 仍可访问业务接口；CORS `allowedOriginPatterns("*") + allowCredentials(true)` 过宽（P2-09/P2-10）。

### 7.2 RBAC 与数据权限 —— 结论：PARTIAL / BROKEN

- 后端 `@RequirePermission` + `PermissionAspect` + Caffeine 缓存 + `RoleMenusChangedEvent` 事件失效：机制完整。
- 权限码三处不一致（详见 P1-07）：SQL 种子（sys_menu.perms）↔ `PermissionConstant.java` ↔ 前端 v-permission。
- 数据权限：`ALL`/`SELF` 有实际语义（mine 过滤），`DEPT` 无部门表、无 dept_id、无 SQL 过滤，声明了但不可实现（P2-01）。

### 7.3 工单生命周期 —— 结论：CODE_VERIFIED

- 创建（强制 CREATED、唯一工单号、路由/物料校验）→ 指派（仅 CREATED/RELEASED 可指派/换派/取消）→ 下达（状态机 CREATED→RELEASED，预校验路由+工序+seq 连续性，乐观锁更新后生成工序记录：首道 READY 其余 PENDING，同事务+唯一索引 `uk_wp_wo_step` 防重）→ 暂停/恢复（IN_PROGRESS↔PAUSED）→ 取消（仅 CREATED/RELEASED，级联取消 PENDING/READY 工序）→ 首工序开工自动转 IN_PROGRESS（`onFirstProcessStarted`）→ 末工序完成自动完工（`onLastProcessCompleted`）→ 关闭。
- 事务：状态更新+工序生成+状态日志同一 `@Transactional`，部分失败整体回滚。
- 幂等：release 由 `@IdempotencyRequired` + `checkWorkOrderIdempotency` 覆盖；pause/resume/close/cancel/assign 未覆盖（P2-07）。

### 7.4 工序执行 —— 结论：后端 CODE_VERIFIED / 小程序前端 CODE_VERIFIED

- 越序校验：`validatePredecessorCompletion` 要求前序 COMPLETED/SKIPPED。
- 重复开始/报工：状态机 + 乐观锁（`accumulateReportQty` 原子 SQL `WHERE version=?`）+ 幂等。
- 报工数量：`accumulateReportQty` 校验不超过计划数量；部分报工保持 IN_PROGRESS。
- 送检/直接完工：`hasInspectionItems(processId)` 决定 WAIT_INSPECTION（自动建检验单）或 COMPLETED（解锁下一道）。
- 小程序请求层（`utils/request.ts`）对 POST/PUT/DELETE 自动附加 `Idempotency-Key`（按“方法+URL+请求体”生成、成功后清除），与后端 `@IdempotencyRequired` 对齐，不存在 400 问题。

### 7.5 质检与返工 —— 结论：后端 CODE_VERIFIED / 前端双端 BROKEN

- 自动建单：`autoCreateInspection` 按 process_record_id 活动唯一约束（生成列 `active_task_key`）防重复；轮次+父单（inspection_round/parent_inspection_id）可追溯；返工完成强制新检验单（REWORK→WAIT_INSPECTION, qc_result='3' 待复检）。
- 录入：只能改 PENDING 单，原子认领 inspector，结果限定 P/F。
- 确认：条件更新 `status='1' AND version=?`，随后同事务联动 `qcPass/qcFail`（QUALIFIED→COMPLETED 或 REJECTED），再推进下一工序——原子性成立。
- 阻断点：
  - P0-01：建表脚本缺 6 列，新环境任何质检单插入/确认都会失败。
  - 小程序质检弹窗：无质检项时提交按钮被禁用、模板内直接改 ref 数组下标不可靠（2026-08-04 已修复）。
  - P1-04：Web 质检页是旧 CRUD 页，没有"录入结果/确认"按钮，且编译失败。

### 7.6 设备维修 —— 结论：后端 CODE_VERIFIED / 前端 PLACEHOLDER（P1-03）

- 报修：`selectByIdForUpdate` 锁设备行，插单并将 `running_status` 置故障。

## 11. 幂等、并发与事务问题

### 11.1 幂等

- 服务端：`pro_idempotency_record` 唯一索引 + INSERT IGNORE 原子占位 + 请求哈希校验 + PROCESSING 超时接管 + markSuccess/markFailure，实现质量高。
- 已复核：小程序请求层自动附加幂等键（原 P1-01 为误报，见第 8 节勘误）。
- 问题 B（P2-07）：Web 只有 release/rework-start/rework-complete 接入；pause/resume/close/cancel/assign/skip/cancel 无幂等。
- 问题 C：Web 质检页无任何调用，enter/confirm 的幂等参数形同虚设。

### 11.2 并发

- 工单/工序状态变更：@Version 乐观锁 + 条件 UPDATE（WHERE status=? AND version=?）双保险，质量高。
- 质检单创建：生成列唯一索引 `uk_qms_active_by_record` 防重复建单（捕获 DuplicateKey 后静默，逻辑成立）。
- 维修/安灯抢单：条件更新防并发，维修还加设备行锁（selectByIdForUpdate），顺序统一。
- 库存：**无任何并发防护**（P1-02）。

### 11.3 事务

- 下达/开工/完工/质检确认/返工等关键链路均 `@Transactional(rollbackFor=Exception.class)`，质检确认联动工序状态在同一事务，原子性静态成立。
- 幂等记录使用 REQUIRES_NEW 与业务事务隔离，业务回滚时允许同键重试，设计正确。
- 风险点：`OperLogAspect`/`StatusTransitionLogService` 吞日志异常（不影响主事务，但审计日志可能静默丢失）。

## 18. 风险、依赖和回滚方案

| 风险 | 说明 | 缓解 |
|---|---|---|
| 质检 DDL 补列 | 新列均允许 NULL/默认值（除 create_time 默认 CURRENT_TIMESTAMP），对存量数据无破坏 | 提供幂等 migration，可重复执行 |
| 密钥轮换 | 微信 AppSecret 轮换会影响线上小程序登录 | 先改环境变量注入，再在微信平台轮换并同步更新 |
| 权限收紧 | 补权限注解后，现有非 admin 角色可能大量 403 | 先做权限码回填与角色授权，再上线收紧；保留灰度开关 |
| 库存重构 | 涉及表结构与历史单据 | 新增流水表不改旧表；单据执行前校验存量数据 |
| 前端重写 | 质检/安灯/维修页重写工作量大 | 按模块分批上线，页面保持向后兼容旧字段 |

回滚方案：所有修复以增量 migration + 新增文件为主，不修改既有表字段语义；前端重写保留旧文件直至新页验收通过。
