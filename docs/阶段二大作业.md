## 1. 设计思路

### 1.1 目标

在既有的自行车装配 MES（Spring Boot 3.3.5 + Vue 3 + MySQL）上增量补齐三项 AI 能力，不重写已有业务：

1. **双端人脸登录**：Web 管理端与微信小程序都支持「纯人脸」和「账号 + 人脸核验」，保留密码/微信登录作为回退。
2. **按用户隔离的私有知识库**：支持 MD/TXT/PDF/DOCX/XLSX/PPTX 的上传、下载、替换、删除，文件落到本地私有目录，分块向量写入 PGVector。
3. **RAG / GraphRAG 问答与知识图谱展示**：问题可走向量检索、图谱检索或两者融合；AI 页面可视化命中的节点、关系和来源，并提供图谱管理入口。

### 1.2 关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 对话模型 | DeepSeek 云端（OpenAI 兼容协议） | 课程允许「使用 API 接入大模型」，不占本机显存，答辩现场最稳 |
| 向量模型 | BGE-M3（1024 维），默认走 SiliconFlow 云端，可一键切本地 CPU | 参数规模与维度匹配，本地 CPU 版本保留作加分演示 |
| 向量库 | 本地 PGVector 容器（宿主 5433） | 数据不出本机，与 MySQL 主库解耦 |
| 图数据库 | 本地 Neo4j 5 Community（7687） | 图拓扑必须落在图库；PGVector 只负责向量检索 |
| 文档解析 | Apache Tika 2.9.2 | 一套 API 覆盖六种格式，不手写解析器 |
| 图谱写入 | 固定参数化 Cypher | 模型只输出受限 JSON，服务端校验类型后写入，禁止模型生成 Cypher |
| 人脸识别 | YuNet（检测）+ SFace（128 维特征）+ MiniFASNet（活体） | 全部本地 ONNX 推理，OpenCV 原生支持 |
| 人脸模板存储 | AES-GCM 密文存 MySQL，照片不落盘 | 隐私优先；匹配在应用层完成，支持 1:1 与 1:N |

### 1.3 数据与隔离模型

- `ai_knowledge_document`：文档清单（`scope` = PUBLIC/PRIVATE、`owner_id`、`content_hash`、`storage_path`）。
- PGVector `vector_store_bge_m3_1024`：`id / content / metadata(json) / embedding vector(1024)`，metadata 带 `source / scope / ownerId / documentId`。
- Neo4j：`(:KnowledgeEntity {id,name,type,scope,ownerId})` 与 `[:RELATION {type,source,scope,ownerId}]`。
- 可见性规则：`PUBLIC` + 本人 `PRIVATE`；管理员只能管理公共库，看不到他人私有数据。
- 人脸：`user_face_template(user_id PK, embedding_ciphertext MEDIUMBLOB)`，一账号一模板。


- Redis（6379，密码 123456）继续承载缓存与索引分布式锁。

### 2.2 后端运行方式

本地以 jar 方式启动，不把后端塞进容器，便于直连本机 MySQL：

```powershell
# application-local.yml（已 gitignore）承载本机连接信息
powershell -File scripts\dev-svc.ps1 start api
# 实际命令行：java -jar bike-assembly-server-1.0-SNAPSHOT.jar --spring.profiles.active=dev,local
```

`application-local.yml` 与 `.env` 的职责分离：`.env` 供 Compose 使用（容器主机名），`application-local.yml` 用 `localhost` 地址供本机 jar 使用。

### 2.3 知识库索引流水线

`AiDocumentIndexService.indexKnowledge()`：

1. 扫描 `AI_KNOWLEDGE_PATH`（本项目为 `D:\xiaoxueqi\docs`），忽略 `target/node_modules/dist/build/.git`。
2. Tika 提取文本 → SHA-256 计算内容哈希。
3. 哈希未变且向量 ID 清单可恢复 → 跳过（增量）。
4. 内容变化 → 先按 `source` 删除旧向量与旧图谱关系，再按 1200 字符 / 160 重叠分块。
5. 调 Embedding（OpenAI 兼容 `/v1/embeddings`）→ 批量写入 PGVector。
6. 调聊天模型抽取实体关系 → 参数化 Cypher 写 Neo4j。
7. 写回 `ai_knowledge_document` 清单（状态、chunk 数、哈希）。

索引是异步任务：`POST /admin/ai/knowledge/index` 返回 `taskId`，前端轮询 `GET /admin/ai/knowledge/tasks/{taskId}`。

### 2.4 图谱管理接口

新增 `AiGraphController` + `AiGraphManagementService`，只读查询和删除都走可见性过滤：

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/ai/graph/overview` | 节点/关系总数、类型分布、公共/私有数量 |
| GET | `/admin/ai/graph/nodes` | 按实体类型、名称关键字分页查询 |
| GET | `/admin/ai/graph/edges` | 按节点、关系类型分页查询 |
| DELETE | `/admin/ai/graph/nodes/{nodeId}` | 删除节点及其关系 |
| DELETE | `/admin/ai/graph/edges?fromId=&toId=&type=` | 删除指定关系 |

### 2.5 人脸登录

- 本地人脸服务：FastAPI + OpenCV，暴露 `POST /v1/face/embedding`。
- 注册：前端摄像头截帧 → 后端转发人脸服务 → 单脸校验 + 活体 → SFace 128 维 → AES-GCM 加密 → MySQL。
- 登录：1:1（带账号）或 1:N（纯人脸）余弦匹配；阈值 0.42，歧义间隔 0.06；失败计入登录锁定。
- 回退：人脸不可用时仍可用密码/微信登录。


### 3.2 图谱抽取的防注入写法

```java
// AiKnowledgeGraphService.java —— Cypher 全部是固定常量，模型只提供参数
tx.run("""
        UNWIND $entities AS entity
        MERGE (n:KnowledgeEntity {id: entity.id})
        SET n.name = entity.name, n.type = entity.type,
            n.scope = $scope, n.ownerId = $ownerId
        """, mergeEntityParams(base, entities));
```

实体/关系类型白名单在 `validateEntities` / `validateRelations` 中校验，模型输出里的未知类型直接丢弃。

### 3.3 可见性过滤（图查询节选）

```cypher
MATCH (n:KnowledgeEntity)
WHERE (n.scope = 'PUBLIC' OR (n.scope = 'PRIVATE' AND n.ownerId = $ownerId))
  AND ($type = '' OR n.type = $type)
  AND ($keyword = '' OR toLower(n.name) CONTAINS $keyword)
RETURN n.id AS id, n.name AS name, n.type AS type, n.scope AS scope, n.ownerId AS ownerId
ORDER BY n.name ASC, n.id ASC
SKIP $skip LIMIT $limit
```

### 3.4 向量文档 ID（增量索引的关键）

```java
String vectorDocumentId = UUID.nameUUIDFromBytes(
        (source + "#" + chunk.index()).getBytes(StandardCharsets.UTF_8)).toString();
```

同一文档同一分块 ID 稳定，重复索引不会产生重复向量；重启后可由 `chunk_count` 反推 ID 清单，从而恢复增量跳过能力。

### 4.3 效果分析

- **RAG 链路**：文档到向量的转换是增量的，二次索引只处理变化文件，符合课程「实时嵌入与更新」的要求。
- **GraphRAG 链路**：图谱与向量共用同一份文档来源，删除/替换文件时两边同步清理，不会出现「有图无文」。
- **隔离性**：文件层、向量 metadata、图谱节点/边三层都带 scope/ownerId，管理员无法读取他人私有数据。
- **性能**：33 个文档全量索引约 5 分钟（云端 embedding + 云端 LLM 抽取）；增量索引在秒级完成。
- **局限**：扫描版 PDF 不做 OCR；语义检索依赖云端额度；本地图谱仅覆盖文档抽取的实体，不包含 MES 业务库的实时图（如工单-工序拓扑）。

## 5. 遇到的问题与解决方案

| # | 问题 | 根因 | 解决方案 |
|---|---|---|---|
| 1 | Docker 引擎未启动，所有容器命令失败 | Docker Desktop 未运行 | 启动引擎并写 `.wslconfig` 限制 WSL 内存为 6GB，避免吃掉 15GB 物理内存 |
| 2 | 索引任务卡住 30 分钟不动 | `deepseek-flash` 是推理模型，长文档抽取时思考 token 耗尽 2048 预算，HTTP 读阻塞 8 分钟 | 抽取输入截到 2500 字符；用 `CompletableFuture.get(45s)` 设硬超时；超时/解析失败只跳过该文档 |
| 3 | 单个文档解析失败导致整批任务失败 | 异常类型为 `NoSuchMethodError`（Error 而非 Exception），外层 `catch (Exception)` 接不住 | 任务层 `catch (Throwable)`，文件层也改为 `catch (Throwable)`，保证状态一定落库 |
| 4 | docx 一解析就 `NoSuchMethodError: TarArchiveInputStream.getNextEntry` | Tika 2.9.2 需要 commons-compress 1.27.x，实际被旧版 1.24.0 覆盖 | 在 pom 中显式钉 `commons-compress 1.27.1` |
| 5 | 修完后仍报 `NoClassDefFoundError: ChecksumInputStream` | commons-io 2.15.1 早于 2.16，缺少该类 | 继续钉 `commons-io 2.17.0` |
| 6 | 重启后索引重复处理全部文档 | 跳过条件依赖 `knownDocumentIds`，但恢复清单时只恢复了哈希 | 按 `chunk_count` 反推 `UUID(source#i)` 恢复 ID 清单，增量跳过生效 |
| 7 | 失败文档写清单时报 `content_hash` 无默认值 | 失败分支把哈希传了 `null` | 失败分支写入空串，保证非空约束的同时保留失败记录 |
| 8 | 索引进程被杀后任务永久 RUNNING、再次提交提示「正在执行」 | Redis 锁 `ai:knowledge:index:lock` TTL 30 分钟不会被主动释放 | 运维手册记录：确认无任务时删除该 key 再重试；后续可在启动时清理孤儿任务 |
| 9 | 人脸服务起不来（503） | MiniFASNet 需要按 checkpoint 校准类别下标，默认 -1 主动 fail-closed | 增加 `FACE_ANTISPOOF_ENABLED` 开关，演示环境关闭活体并返回 `demo-antispoof-disabled` 标记 |
| 10 | Docker 构建人脸镜像超时 | 容器内 PyPI 下载速度约 8KB/s | 演示环境改用本机 Python 启动 uvicorn，镜像构建保留给网络良好的环境 |
| 11 | 迁移到 PostgreSQL 后，并发下报 `current transaction is aborted` | MySQL 一条语句违反唯一键只回滚该语句；PostgreSQL 会中止**整个事务**，后续语句全部失败。原代码 `catch (DuplicateKeyException)` 后继续执行 | 消费留痕改 `PROPAGATION_REQUIRES_NEW` 独立事务；自动建质检单改 `PROPAGATION_NESTED`（SAVEPOINT），冲突只回滚到保存点，外层工序事务继续 |
| 12 | 看板接口在 PG 下报 `function sum(boolean) does not exist` | MySQL 会把 `SUM(status='1')` 当 0/1 求和，PG 的 boolean 不能求和 | 统一改成 `SUM(CASE WHEN … THEN 1 ELSE 0 END)`，共 17 处；`ORDER BY FIELD(...)` 改 `CASE` |
| 13 | 报表数量对不上 / 报工数量可越过计划量 | `UPDATE … INNER JOIN` 是 MySQL 语法，PG 不支持 | 改写为 `UPDATE … SET … FROM … WHERE`，保留 `plan_qty` 上限判断，避免超报 |
| 14 | 上传/替换文件后关键词搜索报 `operator does not exist: json ~~ unknown` | `details_json` 原本是 MySQL `JSON`，PG 的 `json/jsonb` 不支持 `LIKE` | 所有「Java 侧按 String 处理」的 JSON 列统一用 `text`，不加任何 cast；仅校验脚本内部临时 `::jsonb` |
| 15 | 迁移脚本里 `AUTO_INCREMENT`、`DATE_FORMAT`、`@变量`、`JSON_TABLE` 全不认 | 种子文件是 MySQL 方言生成的 1.38MB 脚本 | 重写生成器：日期在 JS 里算好输出字面量，去掉会话变量与临时表；补丁用 `DO $$ … IF NOT EXISTS` 保证幂等；`setval` 修正序列 |
| 16 | MQ 消费端报 `MessageConversionException: Cannot convert from [[B] to [...DTO]` | 自定义 `SimpleRabbitListenerContainerFactory` 只配了连接和并发，没设置 MessageConverter，监听端退回 `SimpleMessageConverter` | 显式 `factory.setMessageConverter(jsonMessageConverter)`，与发送端共用同一个 Jackson 转换器 |
| 17 | 幂等记录 PROCESSING 卡死后永远不会被超时接管 | PG 的 `set_updated_at` 触发器无条件覆盖 `updated_at`，把显式回拨的时间又刷回 now（MySQL 的 ON UPDATE 只在未显式赋值时生效） | 触发器改为「仅当调用方没有改写时间列时才刷新」，用 `IS NOT DISTINCT FROM OLD` 判断 |
| 18 | 质检员在小程序看不到「待检池」 | 种子权限缺 `app:inspection:view-pending`，只有 view / view-all | 补菜单 405 + 授予 inspector 角色 |

## 7. 复现步骤

```powershell
# 1. 基础设施（PG 16 + Neo4j；不需要 MySQL）
docker start xiaoxueqi-pgvector-1        # 关系库 bike_assembly_mes + 向量库 mes_ai 同实例
docker start xiaoxueqi-neo4j-1

# 2. 初始化库（仅首次）
#    docker cp sql\init_database.sql xiaoxueqi-pgvector-1:/tmp/ && psql -f /tmp/init_database.sql …
#    顺序：init_database.sql → patch_ai_reliability_v1.sql → patch_ai_permissions_v1.sql
#         → patch_ai_phase2.sql → dev_seed_full.sql → verify_database.sql

# 3. 人脸服务（本机 Python 方式）
#    前置：models/face 下放好 3 个 ONNX，FACE_ANTISPOOF_ENABLED=false
python -m uvicorn app:app --host 127.0.0.1 --port 8092

# 4. 后端 + 前端
powershell -File scripts\dev-svc.ps1 start all

# 5. 登录后触发索引
#    POST /admin/ai/knowledge/index?maxChars=1200&overlapChars=160
#    轮询 /admin/ai/knowledge/tasks/{taskId}

# 6. 验证
#    /admin/ai/knowledge/status  → vectorStoreStatus = ENABLED、34/34
#    /admin/ai/graph/overview    → nodeCount / edgeCount
#    AI 页面切换 RAG / GraphRAG / 融合 三种检索模式
```
